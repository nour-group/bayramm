# Bayramm

Площадка поиска подрядчиков на праздники в Ташкенте. Telegram Mini App плюс
сайт. Русский и узбекский.

> **Репозиторий публичный.** Спецификации, аудит, планы, юридические и
> бизнес-детали живут в приватном `nour-group/bayramm-internal`, локально —
> в `internal/` (в `.gitignore`). Ничего оттуда не копировать сюда: ни в код,
> ни в комментарии, ни в описания PR и issue. Если папка есть — прочитай
> её `CLAUDE.md`:
>
> @internal/CLAUDE.md

В репозитории — приложения, общий код, миграции и три прототипа
интерфейса (клиент, кабинет вендора, админка).

---

## Монорепо

```
apps/web          клиент: Telegram Mini App + сайт (Vite + React) → Cloudflare Workers (static assets)
apps/vendor       кабинет вендора (Vite + React) → Cloudflare Workers (static assets)
apps/admin        панель оператора (Vite + React) → Workers; вход — хаб на сайте или Mini App из бота
apps/api          сервер (Hono) → Cloudflare Workers
apps/media        варианты фото: /<ширина>/<ключ> → Supabase Storage через Image Transformations
supabase/         миграции и сид Postgres (Supabase)
packages/edge     воркер статических приложений: /api → API, SPA, заголовки безопасности
packages/media    фото: сжатие в браузере, проверка байтов на сервере, ключи и адреса вариантов
packages/tg       Telegram: проверка initData и виджета входа, deep links startapp, секрет вебхука
packages/shared   словари RU/UZ (типизированные), normalizeUz, категории (конфигурация и проверки), контракт API
packages/ui       дизайн-токены (tokens.ts → tokens.css), две темы, тест контраста, свои шрифты (fonts.css);
                  свои контролы на React вместо системных (@bayramm/ui/react + kit.css)
prototypes/       client · vendor · admin — спецификация, не основа кода
e2e/              сквозные проверки в браузере (Playwright + axe): правила продукта, доступность
internal/         приватные документы (клон bayramm-internal, в .gitignore)
```

Пакетный менеджер — **pnpm** (workspaces). Линтер и форматтер — **Biome**.

```bash
pnpm install
pnpm dev:web          # клиент локально
pnpm dev:vendor       # кабинет вендора локально
pnpm dev:admin        # панель оператора локально
pnpm dev:api          # API локально (wrangler dev)
pnpm lint             # biome check
pnpm typecheck        # tsc по всем apps/* и packages/*
pnpm test             # тесты пакетов, приложений и всех трёх прототипов
pnpm e2e              # сквозные в Chromium (один раз: pnpm --filter @bayramm/e2e e2e:install)
```

Окружения: `local` (по умолчанию), `staging`, `production` — блоки `env` в
`wrangler.jsonc` каждого приложения. Секреты — только `wrangler secret put` и
`.dev.vars` (в `.gitignore`), никогда не в репозитории.

Воркеры web, vendor и admin собраны на `createSiteWorker` из `packages/edge`:
`/api/*` уходит в API по сервисной привязке без префикса, остальное — статика с
CSP и прочими заголовками безопасности. CSP пускает только свой origin и не
допускает встроенных скриптов и стилей; нужен внешний источник (шрифт,
`telegram-web-app.js`) — добавить его в `security-headers.ts` явно. Фото с воркера
media — параметр `imageOrigins: mediaImageOrigins(dev)` (только чистый origin). Так сделано
для виджета входа Telegram: опция `telegramLoginPaths` пускает его скрипт и фрейм
`oauth.telegram.org` только на этих путях — у сайта это хаб `/auth`, больше нигде. Колбэк
`data-onauth` виджет исполняет через `eval`, поэтому хаб берёт данные через редирект
`data-auth-url` (`/auth/telegram/<ключ вкладки>`: ключ — в хранилище вкладки, `widgetReturnPath` в
`apps/web/src/hub.ts`; чужую ссылку возврата экран не примет — иначе по подсунутой ссылке человек
вошёл бы в чужой аккаунт). Данные виджета живут 2 минуты, initData для входа сотрудника — 10. Так же `turnstilePaths` пускает скрипт и фрейм
`challenges.cloudflare.com` (проверка «не робот») — у сайта тоже только на `/auth`. Панель —
ещё и Mini App: `telegramWebApp` и `frameAncestors: ["https://web.telegram.org"]`.
Кэш статики — там же (`packages/edge/src/cache-headers.ts`): `/assets/*` (имя с хэшем, в том
числе шрифты) — `public, max-age=31536000, immutable`, страница — `no-cache` (сверка по ETag),
картинки без хэша (`og.png`) — сутки, остальное без хэша (`boot.js`, `robots.txt`) — `no-cache`;
путь `/assets/*`, которого нет в сборке, — 404 `no-store`, а не index.html. Варианты фото
(`apps/media`) — год и `Vary: Accept`. Только HTTPS — у всех воркеров (`packages/edge/src/https.ts`:
сайт, кабинет, панель, API, media): запрос по http — 301 (GET, HEAD) или 308 на тот же адрес с https
(localhost — без редиректа), ответы — `Strict-Transport-Security: max-age=31536000` (без
includeSubDomains и preload — каждый поддомен ставит его себе). Проверяет и smoke-тест выкладки.

### Аккаунт: один на все роли

Человек — одна запись `app.accounts`; способы входа — `app.account_identities`
(`telegram` и `phone`, значение — HMAC от `ID_HASH_KEY`, у каждого способа один
владелец); клиент, партнёр вендора (`app.vendor_users`) и сотрудник (`app.staff`) — роли
с `account_id`. Имя из Telegram — `pii.account_profiles`. Слияния аккаунтов нет: способ,
который уже у другого аккаунта, не добавляется (`identity_taken`). Сессия (`app.sessions`)
всегда принадлежит аккаунту: `kind` account — 7 дней, staff — 12 часов и только по
входу не старше 12 часов (`proof_at`); отключение сотрудника или аккаунта отзывает сессии.

Входы (`apps/api/src/routes/auth.ts`): initData Mini App (`POST /auth/telegram`, кабинет —
с `app: "vendor"`), виджет на хабе (`POST /auth/widget`), код по телефону
(`POST /auth/phone/send` → `/verify`: 3 кода за 10 минут на номер и на IP, 5 попыток,
код живёт 10 минут, повтор через 60 секунд, хранится HMAC). Отправитель кода —
`OTP_PROVIDER`: `off` (вход по телефону выключен), `console` (только `APP_ENV=local`),
`tg_gateway` (Telegram Gateway, секрет `TELEGRAM_GATEWAY_TOKEN`). `GET /auth/methods` —
чем можно войти и адреса приложений; `GET /me` — аккаунт, способы входа и роли. Тексты входа
(хаб, профиль, кабинет, панель) упоминают телефон, только если `phone: true`. Старые
`/auth/vendor/telegram` и `/auth/staff/telegram` приложения не вызывают: они устарели, остаются
для старых сборок и пишут каждое обращение в лог (`auth.legacy`) — удалить, когда обращений нет.
Тесты их не используют: на каждый — один явный интеграционный тест «работает и пишет в лог».

Код на телефон просит человек (`apps/api/src/auth/turnstile.ts`): с секретом
`TURNSTILE_SECRET_KEY` `POST /auth/phone/send` из браузера принимает только токен Cloudflare
Turnstile (виджет — в хабе, ключ `TURNSTILE_SITE_KEY` отдаёт `GET /auth/methods`), Mini App —
свою `initData`, и только вместе с сессией аккаунта того же пользователя Telegram (initData получит
любой бот-аккаунт) и не чаще `RATE_LIMIT_OTP_ACCOUNT` на аккаунт. Siteverify — с `remoteip`, `idempotency_key`, action `phone_code` и сайтом
окружения (`WEB_APP_URL`); сбой — отказ (503). Без секрета проверки нет. Поэтому телефон к
аккаунту на сайте добавляется в хабе (`/auth?link=phone`), в Mini App — прямо в профиле.

Кабинет и панель вне Telegram входят через хаб на сайте (`apps/web/src/screens/SignIn.tsx`):
уводят браузер на `<сайт>/auth?app=…&state=…&challenge=…` (PKCE S256,
`@bayramm/shared/pkce`), хаб после входа берёт одноразовый код (`POST /auth/hub/code`:
60 секунд, один раз, привязан к приложению, его origin, state и challenge) и уводит на
`<приложение>/auth/callback`; приложение меняет код + verifier на свою сессию
(`POST /auth/hub/exchange`). Общих cookie между поддоменами нет. Панель затем повышает
сессию аккаунта до сессии сотрудника (`POST /auth/staff/elevate`) и сразу отзывает
первую; в Telegram — `POST /auth/staff/webapp` по initData. Ссылка с `?signin=1` из
другого приложения сразу уводит в хаб; внутри Telegram ссылки на другие роли идут через
бота (`?start=cabinet|admin`, `?startapp`). Партнёр нескольких вендоров выбирает кабинет:
заголовок `X-Bayramm-Vendor` (без него — 409 `vendor_choice_required`).

Сотрудники входят по приглашению: запись в `app.staff` с
`pii.staff_profiles.telegram_username` или `app.staff.phone_hash`; приглашение принимает первый
вход аккаунта с этим Telegram или номером — оно привязывается к аккаунту. По телефону
приглашают из «Команды» (`app.staff_invite_phone`, через `apps/api/src/db/pii.ts`): хранится
только HMAC номера; номер, уже подтверждённый у аккаунта, принимает приглашение сразу. Так же его
принимает первое сообщение боту (имя пользователя — из подписанного обновления).
`/start` показывает кнопку каждой роли аккаунта (панель, кабинет, приложение) на языке,
сохранённом в профиле, иначе — на языке Telegram; сотруднику — карточку команды, `/stats`
и `/admin`. Приглашает, меняет роль и отключает администратор в разделе «Команда»
(функции `app.staff_invite`, `app.staff_set_role`, `app.staff_set_active`): себя — нельзя,
последнего действующего администратора база не отключит и не понизит никаким путём
(действующий — принявший приглашение: роль на аккаунте). Приглашение, которое ещё не приняли
(ни входа, ни действий), администратор отзывает — `DELETE /staff/team/:id`
(`app.staff_revoke_invite`); принятое — только отключить (409 `staff_invite_accepted`).
Виджет входа работает на одном домене бота: у бота каждого окружения в @BotFather
`/setdomain` — домен сайта этого окружения, тот же в `TELEGRAM_LOGIN_DOMAIN` API.

Пользователей кабинета вендора тоже приглашают — администратор или менеджер на странице вендора
(«Вход в кабинет», `apps/admin/src/pages/VendorUsers.tsx`; `POST /staff/vendors/:id/users` →
`app.staff_invite_vendor_user` через `db/pii.ts`): имя, телефон, роль (`owner` | `member`, в панели —
явным выбором) и язык уведомлений. Принимает приглашение первый вход аккаунта, доказавшего номер
(контакт в боте, код на телефон); номер, уже подтверждённый у действующего аккаунта, — сразу. В
панели у каждого — статус (ждёт входа / вошёл / отключён), доходят ли уведомления (`notifiable`:
Telegram привязан и бот знает чат), последний вход (Mini App и обмен кода хаба в кабинет) и текст
приглашения на языке партнёра (бот `?start=partner`, кабинет `?signin=1&lang=`,
`apps/admin/src/vendor-invite.ts`). У кабинета с действующими пользователями всегда есть действующий
владелец — триггер `app.vendor_keep_owner` (409 `vendor_last_owner`): последнего не понизить, не
отключить и не убрать, сотрудника площадки без владельца не пригласить. Он проверяет итог оператора:
удалить всех пользователей вендора одним оператором можно; функция, которая удаляет вендора по шагам,
ставит `set_config('app.deleting_vendor', <id вендора>, true)`. Убрать из кабинета —
`DELETE /staff/vendors/:id/users/:userId` (`app.staff_remove_vendor_user`, DELETE у API на таблицу
нет): сессии до аккаунтов, неотправленные уведомления и профиль — вместе с ним, аккаунт остаётся.
Членство получило аккаунт с Telegram любым путём — чат для уведомлений берётся из известного об
аккаунте (другой кабинет, роль сотрудника, клиент, которому бот пишет), и партнёру один раз уходит
`vendor.access_granted` («вас добавили в кабинет»). Партнёр сам пользователей кабинета не заводит —
только команда (`apps/api/src/vendor/access.ts`).

Имя бота нигде не вписано: у каждого окружения свой бот, API узнаёт его по
токену (`getMe`, кэш на час) и отдаёт в `GET /api/telegram/bot` вместе с
адресом Mini App (`WEB_APP_URL`), а также в `GET /api/auth/methods`; приложения берут
имя оттуда. Команды, описания и
кнопку меню задаёт код — `apps/api/src/telegram/bot-profile.ts`; деплой
применяет его через `POST /telegram/sync` (секрет `TELEGRAM_SYNC_KEY` в воркере
API и в GitHub Environment). В @BotFather вручную — только `/setdomain` и
основное Mini App.

Бот принимает сообщения вебхуком `POST /telegram/webhook` (его ставит тот же
`/telegram/sync` на `API_URL`; секрет выводится из `ID_HASH_KEY`). Вендор
привязывает Telegram, поделившись своим контактом: номер сверяется с
`app.vendor_users.phone_hash` = HMAC(`ID_HASH_KEY`, «+998XXXXXXXXX») —
`phoneHash` в `apps/api/src/auth/crypto.ts`, привязка — `app.vendor_user_claim_telegram`
(номер уникален внутри вендора: один человек бывает партнёром нескольких). Вход аккаунта
с этим номером по коду привязывает к нему все такие записи.
Кабинет вендора — `VENDOR_APP_URL`. Карточку партнёр меняет предложением правки
(`/vendor/listings/:id/revisions` → `app.listing_revisions`: название, описания, поля витрины,
ссылки на видео; одна открытая на площадку, в правке только изменённые поля; цен в правке нет —
они в услугах, см. «Категории и услуги»; ключи проверяет база у открытой правки), решает
команда в «Модерации»;
клиент до решения видит прежнюю карточку. Фото партнёр загружает сам
(`/vendor/listings/:id/photos`: тот же путь, что у сотрудника — `compressForUpload`,
`assertUploadable`, `X-No-Faces: 1`); новое фото ждёт решения модератора и клиентам не видно;
отклоняют фото только с причиной (`app.photos.moderation_reason`, есть лишь у отклонённого) — партнёр
видит её у фото;
фото любой витрины, кроме отклонённой (и черновика: партнёр видит «на проверке»), —
`ops.photos_submitted` команде и очередь «Новые фото» в «Модерации». Черновик (и отклонённую —
через черновик) владелец кабинета отправляет на проверку сам: «Отправить на проверку» в
чек-листе витрины (`Readiness`), когда его пункты сделаны (`reviewBlockers` — что мешает отправить:
услуги и фото, ждущие решения, засчитаны), — `POST /vendor/listings/:id/submit` (`vendor/submit.ts`;
не готово — 422 `publish_blocked`), тем, кто публикует, — `ops.listing_submitted` (от партнёра и от
менеджера). Роли партнёра (`app.vendor_users.role`): карточку — правки и фото — меняет
только владелец (`owner`), заявки и календарь ведёт и сотрудник площадки (`member`) —
`apps/api/src/vendor/access.ts`, в базе — `app.edits_listing` в политиках. Опубликованную
карточку менеджер (без права модерации) тоже меняет правкой: название и описания PATCH
отправляет на модерацию (`sentForModeration`), остальное сохраняет; база — BR005.
Календарь: прошедший день по Ташкенту не меняет никто (BR024 → `date_out_of_range`), правка —
только от версии, которую видел человек (`app.availability_versions`; кабинет — `If-Match`,
панель — `version`; устарела — 409 `calendar_conflict`). Уведомления ставят в `app.outbox` триггеры
базы (в payload только id), отправляет cron API раз в минуту; маршрут, после
которого ждать минуту не хочется, вешает `outboxKick`
(`apps/api/src/notify/kick.ts`). SLA 12 часов — там же, по cron. «Связались», отмеченное
сотрудником (`first_response_by = staff`), клиенту — не «площадка ответила», а «команда
связалась с площадкой»; новая правка карточки — `ops.revision_submitted` тем, кто решает по правкам.
Оповещения о витрине (услуги, фото, отправка на проверку) ставит `app.enqueue_listing_alert`
(`20261011090000_moderation_flow.sql`): пока у получателя есть неотправленное (pending, failed) о той же
витрине, второе не ставится — текст («ждут решения: N») собирается при отправке; отправленное новому
не мешает (раньше ключ «витрина + час» терял всё после первого за час). У оповещений команды — кнопка
в панель (`ADMIN_APP_URL`: «Модерация», витрина, правка). Оповещения команды получает только тот, у
кого бот знает чат (`/start`); некому отправить — строка журнала `outbox.no_recipients` (вид и
витрина, раз в час); `GET /staff/me` и «Команда» отдают `botLinked`, и тому, кто решает по
модерации без чата, панель показывает просьбу написать боту, в «Команде» — «бот: нет».

Лимиты частоты — привязки Workers Rate Limiting (`ratelimits` в
`apps/api/wrangler.jsonc`, `apps/api/src/ratelimit.ts`): `POST /auth/*` по
HMAC от IP, `POST /requests` по IP и по клиенту, `POST /catalog/listings/:slug/contact` по IP,
код на телефон из Mini App — по аккаунту; IPv6 считается сетью /64 (`limitAddress` в `auth/ip.ts`, и
у лимита кодов в базе); превышение — 429
`rate_limited` с `Retry-After`. Привязки не наследуются окружениями, у каждого
окружения свои `namespace_id` (проверяет `config.test.ts`).

Сроки хранения и истечение заявок — `app.run_daily_maintenance()` (раз в день
по Ташкенту, повтор в тот же день ничего не делает); запускает его шаг
`daily_maintenance` того же cron в окне 21:00–21:59 UTC
(`apps/api/src/maintenance`). За ним — сверка фото с хранилищем (`apps/api/src/photos/sweep.ts`):
строки фото, удалённые больше 30 дней назад, — вместе с объектами, объекты без строки старше
суток; за запуск — ограниченно, в лог — только числа. Отдельный Cron Trigger не заводить — их мало на
бесплатном тарифе. Права клиента на свои данные — `GET /me/export`,
`POST /me/consents/withdraw`, `DELETE /me` (функции `app.client_*`, только над
собой); выгрузка и отзыв согласия — и заблокированному клиенту (`requireClient` с `allowBlocked`).

Избранное («Сохранённое», вкладка клиента): у вошедшего — `app.favorites` (строки видит только
сам клиент; добавляют только `app.client_favorite_add` и `app.client_favorites_merge`, не
больше 100), `GET/PUT/DELETE /me/favorites/:listingId`; у гостя — id в localStorage и карточки
`GET /catalog/cards?ids=…`. При входе гостевой список сливается с аккаунтом и из браузера
стирается. Снятая с публикации площадка из списка просто пропадает; выгрузка своих данных
его содержит, удаление аккаунта стирает. localStorage в клиенте — только это и язык гостя
(`apps/web/src/storage.ts`), токен и черновики — во вкладке. Доступность staging и production каждые 15 минут проверяет workflow
`Uptime`.

Контакты витрины — по кнопке «Связаться» (`apps/web/src/components/ContactSheet.tsx`), до заявки и
без входа. Витрина (`GET /catalog/listings/:slug`) несёт только `contactChannels` — какие каналы есть;
номер и Telegram отдаёт `POST /catalog/listings/:slug/contact` с `action: "open"` (ответ не
кэшируется), выбор «Позвонить» или «Написать в Telegram» — тот же маршрут с `phone` / `telegram`
(204). События — `app.contact_events`: витрина, действие, источник (tma / web) и вошёл ли — без
клиента (ПДн); открыть контакты можно только вместе с событием (`pii.reveal_listing_contacts`).
Сводка «у кого чаще ищут связь» — `GET /staff/metrics/contacts` (`app.metrics_contacts`; в панели — блок
«Контакты витрин» в «Метриках», 30 дней и фильтр категории). Telegram
витрины — `pii.listing_contacts.public_telegram` (только имя, без @; задаёт сотрудник рядом с
телефоном витрины, `normalizeTelegram` принимает и ссылку t.me). Клиенты в панели — по имени из Telegram
(«Азиза К.»), способам входа и последней заявке; код `C-…` — вторым текстом, по нему и ищут.

Демо-залы для показа — только staging: workflow `Demo data (staging)` (seed / reseed / reset /
check) рисует фото — иллюстрации по категории с плашкой DEMO (`apps/api/scripts/demo-photos.ts`) —
и зовёт `POST /ops/demo` (`apps/api/src/demo`). Seed заводит три зала и по две витрины в каждой
другой включённой категории (услуги, поля витрины, занятость) с пометкой «Демо» теми же шагами,
что панель, и уже заведённое не меняет — новые тексты и фото только через reseed; reset
(`app.demo_purge()`) убирает только их — id из диапазона
`00000000-0000-4000-8000-de…` — с заявками и фото. Вне staging и без секрета `DEMO_SEED_KEY` — 404.
После seed и reseed (и режимом check) тот же workflow проверяет staging в браузере
(`e2e/staging`, `playwright.staging.config.ts`): лендинг, каждый раздел и каждую его витрину, фото
с media, «Связаться», узбекский, занятый день.
Чего в production быть не должно, проверяет чек-лист выпуска `.github/scripts/release-check.sh`
(последний шаг выкладки production; вручную — `bash .github/scripts/release-check.sh bayramm.uz`):
демо-витрины в каталоге, тестовый бот, вход по телефону без Turnstile, черновики согласий («ЧЕРНОВИК» /
«QORALAMA», `supabase/demo/*.draft.sql`) и отсутствие действующих текстов трёх целей клиента. Утверждённые
тексты выходят шаблоном `supabase/legal/consent-texts.template.sql` (копия с текстами — вне публичного
репозитория; следующая версия цели и языка, прежние — из оборота; незаполненное, черновик, апостроф или
один язык из двух откатывают его целиком); с
`SUPABASE_DB_URL` — ещё и база (черновики у целей вендора, строки демо-диапазона, телефоны +998 00 у
опубликованных витрин — в карточке их нет). Production выкладывается только из `main` или тега `v*`;
у всех воркеров `workers_dev` и `preview_urls` выключены (только свои домены); ответы `/staff/*`,
как и кабинета, — `no-store`.

Метрики запуска («заявка → ответ площадки за 12 часов») считает только база:
факты заявки — представление `app.request_metric_facts`, суммы — функции
`app.metrics_*` (миграция `20260930220000_launch_metrics.sql`, там же определения; категории —
`20261002090000_services_only_category_metrics.sql`). Категория заявки — категория витрины:
фильтр `?category=` у недель и вендоров (`/staff/metrics`, `/staff/metrics/vendors`), сводка —
`GET /staff/metrics/categories` (`app.metrics_categories`), у витрин вендора — категория.
Ответ площадки — её первый переход в contacted/deal/declined по
`app.request_status_log`; «связались» от сотрудника, просмотр и звонок — не ответ.
Панель — раздел «Метрики» (очереди «Сейчас» — плитка ведёт в раздел, где очередь разбирают;
сводка по категориям, недели и вендоры с фильтром категории) и блок на странице вендора (витрины с категориями; право `metrics.read`); те же функции собирают отчёты бота администраторам: сводка каждое
утро и недельный по понедельникам (`app.enqueue_ops_reports`, шаг `ops_reports`
cron в окне 04:00–04:59 UTC, один раз за день и неделю). Ответ API 5xx —
`app.record_api_error` из `app.onError` после ответа: оповещение `ops.api_error` не
чаще раза в 30 минут, только метод и шаблон маршрута. Пауза между напоминаниями
вендору от сотрудника — настройка `ops_reminder_pause_minutes`
(`app.ops_reminder_pause()`). Workers Logs включены у всех воркеров
(`observability`; у клиента — каждый десятый запрос).

### Категории и услуги

Источник правды — `packages/shared/src/categories/config.ts` (`CATEGORIES`, импорт
`@bayramm/shared/categories`), тексты — `packages/shared/src/i18n/categories` (ru, uz; ключ подписи
проверяет компилятор). Категория описывает: режим занятости (`day` — день целиком; `parts` —
утро, день, вечер, окна по умолчанию 05–11, 11–17, 17–24, своя категория переопределяет
`dayParts`; `slot`; `lead` — срок подготовки), правило фото (`no_people` — отметка «без лиц»,
`X-No-Faces: 1`; `portfolio` — она или согласие людей на фото, `X-Photo-Consent: 1`), минимум фото,
ссылки на видео (только YouTube и Instagram, хранится канонический вид), поля витрины
(`attributes`: тип, обязательность, фильтр каталога `?a.<поле>=`), форму заявки (`details`; гости —
required, optional или hidden) и каталог услуг (единицы цены, опции-шаблоны, `tier`, входит ли в
цену «от»; «другая услуга» `other` — своё название и всегда через модерацию). Проверки —
`validate.ts`, одни и те же в API и интерфейсах; контракт — `@bayramm/shared/api` (клиент),
`…/api/staff`, `…/api/vendor`, `…/api/services`.

Витрина — карточка (`app.listings`) в одной категории: свои поля, услуги, фото, занятость и
заявки. У вендора витрин может быть несколько (`POST /staff/vendors` с `categoryCode`,
`POST /staff/vendors/:id/listings` → `app.staff_add_listing`); пользователи кабинета, контакты,
согласия и чек-лист — общие у вендора. Категорию меняет только сотрудник и только пока у витрины
нет заявок и услуг (`POST /staff/listings/:id/category`, иначе 409 `category_locked`).
Удалить витрину (`DELETE /staff/listings/:id`, администратор и менеджер) или вендора целиком
(`DELETE /staff/vendors/:id`, администратор; в панели — подтверждение кодом вендора) можно,
только пока ни по одной его витрине не было заявок и ни одна не на проверке и не в каталоге
(`app.staff_delete_listing`, `app.staff_delete_vendor`; иначе 409 `listing_in_use` /
`vendor_in_use`, причина — `requests` или `published`; заранее её отдаёт `deleteBlocker`
витрины и вендора) — иначе приостановить. Уходят фото, услуги, занятость, контакты, правки,
пользователи кабинета и оповещения о них; история статусов, журналы и согласия остаются, в
журнал — одна запись `listing.delete` / `vendor.delete` с числами. Объекты фото API удаляет
после фиксации, не удалились — уберёт ежедневная сверка.

Услуги — `app.listing_services`: draft → review → active, rejected, paused. Модератор и
администратор решают сразу; менеджер и партнёр отправляют на проверку, правка активной услуги
опубликованной витрины — предложением (`proposal`), клиент до решения видит прежнее. Очередь —
`GET /staff/services` (у любой витрины, кроме отклонённой, — и у черновика; там же решают на странице
витрины: «Одобрить» и «Отклонить» с причиной), решение — `vendor.service_decided` владельцам кабинета
(одобрение — у опубликованной витрины: публикация одобряет пачкой; отказ — у любой; кнопка — в
«Услуги» кабинета), новая услуга или предложение — `ops.service_submitted` команде. Отклонённая,
сохранённая партнёром черновиком (`submit: false`), — черновик. Цена «от» карточки выводится из услуг с
`in_price_from` и руками не задаётся (столбцы цены пишет только триггер, у роли API права нет).
Готовность к публикации — `app.listing_publish_blockers` по правилам категории (`attributes`;
`packages` — код блокера «нет обязательных услуг категории»; фото — минимум категории). Пакетов
залов v0.1 больше нет (`20261002090000_services_only_category_metrics.sql`): цены — только
услугами, ни в ответах API, ни в правке карточки пакетов и цены нет.

Занятость `parts`: отметки частей — `app.availability_parts`, заявка несёт `day_part` (из
`details.start_time`); часть занята, когда отметок и активных заявок не меньше
`parallel_capacity` витрины (по умолчанию 1, `PUT …/calendar/capacity`); `app.listing_busy`,
`app.listing_day_load` (free, partial, busy). Выдача каталога на дату считает загрузку одним
запросом на категорию — `app.catalog_day_load` (те же правила; сверяет pgTAP), а не функцией на
каждую строку; обложки — по частичному индексу `photos_public` под политикой `photos_read` без
вызова функций на строку у гостя. Отметка дня целиком (`app.availability`) — весь день;
версия календаря и запрет прошедших дней — те же. Заявку на занятый день или занятую часть дня
API не принимает — 409 `date_busy` (details `eventDate` или `details.start_time`; та же
`app.listing_busy`, что у каталога и витрины). Карточка витрины отдаёт занятость на весь срок, на
который клиент выбирает дату в каталоге (`BUSY_DAYS_AHEAD` = 366), иначе каталог и витрина
расходились бы на дальних датах.

`tier` (base | extra) и `app.service_allowed(vendor, category, type)` — единственная точка для
будущей проверки тарифа; сейчас всегда true и ни на что не влияет — ни на выдачу, ни на порядок.

Включённые категории — `enabled` в конфигурации (staging и production одинаково); клиент берёт
`GET /catalog/categories` и пустые (без опубликованных витрин) не показывает. Порядок показа (`sort`) —
путь пары: ЗАГС, тойхона, кортеж, фото и видео, студия, ресторан, цветы, наряды, подарки, кейтеринг
(код `food`), торты, декор; выключены — музыка и аниматоры (только «другая услуга»). Списки категорий
в приложениях сортируют по `sort`, а не по порядку кодов. Новая категория или тип услуги:

1. правка `config.ts` и `i18n/categories/{ru,uz}.ts`;
2. новая единица цены — `alter type app.price_unit add value` отдельной миграцией (в одной
   транзакции с использованием нельзя);
3. `pnpm --silent --filter @bayramm/shared categories:sql` — сид; новая миграция с ним (и
   rollback). Последний сид сверяет с конфигурацией `apps/api/src/db/categories-seed.test.ts`,
   базу — интеграционный `categories.test.ts`.

Код категории и типа услуги после выпуска не меняется: на него ссылаются карточки и заявки.

Формы панели и кабинета строятся по конфигурации, а не пишутся под категорию: помощники —
`packages/shared/src/categories/forms.ts` (поля витрины в форме и правка только изменённого,
ссылки на видео, услуга с добавками, поля заявки для показа, предложение правки услуги «было →
стало»); ошибки — те же пути, что в ответе 422 (`attributes.fleet.0.class`, `options.1.priceUzs`).
Панель: новый вендор — только с категорией первой витрины; витрина в другой категории —
`/vendors/:id/listings/new`; смена категории — блок «Категория» витрины (пока нет услуг; заявки
проверяет сервер — `category_locked`). Форма витрины (`pages/ListingForm.tsx`,
`AttributeFields.tsx`): вместимость — у `guest_capacity`, видео — у `maxVideoLinks`, «заказов
одновременно» — у `parts`; цен в форме нет — они в услугах (`pages/Services.tsx`). Фото — отметка
по `photoPolicy`. Занятость (`pages/Calendar.tsx`): day и slot — дни, parts — день открывается
частями с местами, lead — срок заказа без календаря. Очередь услуг — в «Модерации»; заявки —
фильтр `?category=` (как и вендоры), часть дня и что нужно клиенту. В e2e у подмены API панели
`seeded: true` — витрины кортежа, фото и тортов с услугами и заявкой (`e2e/support/staff-catalog.ts`).

## Что делать в первую очередь

Первый запуск — **одна категория, залы Ташкента, 30–50 штук**. Цель не
«сделать платформу», а доказать: клиент отправляет заявку, вендор отвечает
за 12 часов.

Порядок:

1. Инфраструктура, схема БД, аутентификация
2. Кабинет вендора: вход, карточка, календарь, заявки
3. Заявка end-to-end: запись в БД, уведомление вендору в Telegram, статусы
4. Клиентское приложение на реальных данных вместо вписанных
5. Админка: модерация вендоров

Не начинать с премиума, рекламы, подписок, статистики и остальных семи
категорий. Они во вторую очередь.

## Правила продукта — нарушать нельзя

Они не про стиль, а про суть продукта. Каждое проверяется тестами в
`prototypes/client/smoke.js`, на живом клиенте — `e2e/web/rules.spec.ts`.

| Правило | Что это значит в коде |
|---|---|
| Клиент не платит | Ни комиссий, ни платы за заявку. Деньги через нас не идут |
| Заявка, не бронь | Слово «забронировать» запрещено в интерфейсе и словарях |
| Телефон виден сразу | Номер (и Telegram) вендора — одним нажатием «Связаться» до заявки и без входа, не после |
| Цена обязательна | Вендор без цены не публикуется. «По запросу» не допускается |
| Фото обязательны | Минимум 3. Без фото карточка не публикуется |
| Реклама помечена | Каждый оплаченный блок несёт слово «Реклама» |
| Согласие не предзаполнено | Раздельно по целям, кнопка отказа того же размера |
| Место в выдаче не продаётся | Оплата не влияет на сортировку по цене и рейтингу |
| 12 часов на ответ | Не ответил — клиенту показываются похожие |

Последнее — обязательство, данное клиенту в интерфейсе. На сервере нужен
счётчик и эскалация.

## Соглашения

### Двуязычность

Словари — в `packages/shared/src/i18n` (`ru.ts`, `uz.ts`). Тип `Dict`
выводится из `ru`, `uz` обязан ему соответствовать — лишний или пропущенный
ключ не компилируется. В строках нет HTML: богатый текст — структурные блоки.

Узбекский — латиница. Апострофы: `ʻ` (U+02BB) после o/g — `oʻ`, `gʻ`;
`ʼ` (U+02BC) — tutuq belgisi. Прямые и кавычки-апострофы запрещены тестом;
для поиска — `normalizeUz()`. *Соглашение ждёт подтверждения владельцем текстов.*

Глоссарий клиента (сайт и Mini App) — `packages/shared/src/i18n/glossary.ts`: одно понятие —
одно слово на обоих языках (исполнитель / hamkor, заявка / soʻrov, раздел каталога, единицы цены,
части дня). Запрещённые слова («вендор», «ariza»…) ловят `i18n.test.ts` и `e2e/web/rules.spec.ts`;
в ключах из прототипа «вендора» заменяет скрипт переноса. Короткие названия разделов для клиента —
`catName` словаря (у кабинета и панели — свои, из `@bayramm/shared/categories`); что в разделе
одной строкой — `catDesc` (плитка лендинга с планшета, шапка каталога раздела, описание для
поисковиков — `categoryDesc`).

### Дизайн-система

Источник правды — `packages/ui/src/tokens.ts`; `tokens.css` генерируется из
него (`pnpm --filter @bayramm/ui css`). Две темы: основная и премиум («Suzani»).

**Тема обязана переопределять базовые токены, а не отдельные классы.** Иначе
любое правило с `--muted` или `--coral` остаётся от светлой темы, и дыры
находятся бесконечно.

Шкалы: кегли 10–27 из фиксированного набора, скругления 3·8·11·14·18·22·999,
зазоры 3·5·7·9·12, отступы только чётные, иконки 12·14·17·20·24·26.

Зона нажатия минимум 44px — расширять невидимым слоем, не увеличивая рисунок.

### Контролы — только свои

Системные `<select>`, `<input type="checkbox|radio|number|date|file|search">`,
`<dialog>`, `window.confirm/alert/prompt` и подсказки `title=` в приложениях не
используются: в Telegram и старых вебвью они выглядят чужими, а список и календарь
не знают про безопасные зоны. Вместо них — `@bayramm/ui/react`: `Select`, `Combobox`
(список с поиском: варианты подбирает приложение, поле поиска — combobox), `Checkbox`,
`Switch`, `RadioGroup`, `NumberStepper`, `DateField`/`Calendar`, `FileDrop`, `SearchField`,
`ConfirmSheet`/`Dialog`, `useToast`, `Tooltip`, а для связи —
`ConnectivityProvider` + `OfflineBanner` (события online/offline; загрузчики экранов
повторяют упавший без сети запрос через `useOnReconnect`); стили —
`@bayramm/ui/kit.css` (подключать между `tokens.css` и стилями приложения). Под
рисунком галочек, радиокнопок и выбора файлов — настоящий `<input>`. Список и
календарь на телефоне — шторка снизу, на компьютере — панель у поля; страница под
ними inert. Слов в наборе нет: «Закрыть»/«Очистить» — `UiTextsProvider` в корне
приложения, остальное — пропсами. Страж — `packages/ui/src/react/native-controls.test.ts`.

### Панель оператора на телефоне

Панель — каждый день Mini App на телефоне. Раскладку выбирает `apps/admin/src/layout.ts`
(`useLayout`; те же границы — в `@media` `styles.css`): до 719px — телефон (шапка `.appbar`:
«назад», заголовок, аккаунт; нижняя панель разделов роли — `tabsFor`: кнопками только
ежедневные разделы (`TAB_SECTIONS`, названия целиком влезают и на 320px — сокращений нет),
влезает пять, больше — четыре и «Ещё» в шторке; уведомления, журнал, команда, настройки — всегда
в «Ещё»; счётчики — очереди `GET /staff/metrics?weeks=1`, у «Модерации» — только те, по которым роль
решает, `badgesOf`), 720–1023px —
колонка разделов слева, шире — шапка с разделами. Списки на телефоне — карточки (`.rcards`,
вся карточка — ссылка `.rcard-link`), фильтры и сортировка — в шторке (`FilterButton`,
«Фильтры (n)»); таблица, которой нужно остаться таблицей, прокручивается вбок в своей рамке
с тенью у края. Главные действия экрана — `ActionBar` (на телефоне прилипает к низу над
нижней панелью: оболочка кладёт место `.actionbar-slot` последним в страницу, поэтому в конце
страницы панель ничего не закрывает), второстепенные — `OverflowMenu`, причина и
комментарий — `PhoneSheet`, необратимое — `ConfirmSheet`, «Сохранить» — `FormBar` (на телефоне —
в панели действий и только когда есть что сохранять). Поля — 16px (иначе iOS увеличивает
страницу). В Telegram — `initTelegram` (цвета из токенов, без сворачивания свайпом),
`BackButton` на вложенных экранах (`goBack`: по истории панели, открыли по ссылке — к
разделу), высота — `--tg-viewport-stable-height`. Экраны — ленивые куски (`screens.ts`),
тесты jsdom грузят их заранее (`src/test-setup.ts`); React — свой кусок (`vite.config.ts`),
конфигурация категорий — общий кусок экранов: `CategoryChip` и подписи — в `categories.tsx`, в
`ui.tsx` их не класть (иначе она снова в основной части). Проверки — `e2e/admin/mobile.spec.ts`
(проект `admin-phone`: каждый экран на 320, 360 и 390px).

Разделы — один порядок на всех ширинах (`NAV`, `router.ts`): кнопки нижней панели, потом
уведомления, журнал, команда, настройки. Главный экран — `homeOf`: первый раздел нижней панели,
доступный роли (администратор и менеджер — «Заявки», модератор — «Модерация»); туда ведут корень,
вход, «не найдено» и «нет доступа». Страница объекта на компьютере — путь над заголовком
(`useBreadcrumbs`: витрина → вендор; заявка и предложение изменений — вендор → витрина; клиент —
«Клиенты»), на телефоне и планшете — «назад» в шапке и ссылки на вендора и витрину в шапке
страницы. Фильтры, поиск и страница списка — в адресе (`useQueryState`, replaceState: номер записи
и прокрутка в `history.state` целы): вендоры `q status category page`, заявки
`q sla status category listingId page`, клиенты `q blocked page`, метрики `category`, модерация
`queue` (к очереди), журнал — как был; ссылка с `View.query` ведёт сразу на отфильтрованное
(`/requests?sla=late` — плитка просрочки, `?q=V101` — «Заявки вендора», `?listingId=` — «Заявки
витрины», `/listings/:id?focus=photos` — к блоку). Переход монтирует экран заново
(`Arrival.seq`), «назад» возвращает прокрутку, когда список догрузится (`restoreScroll`). Поиск —
без кнопки, с задержкой (`useListSearch`). Длинный список не обрезается молча (`usePagedList`):
на компьютере `Pager`, на телефоне «Показать ещё» дописывает следующую страницу; пусто из-за
фильтров — «Сбросить фильтры» (`EmptyList`). Тупиков нет: заявка → клиент (`client` — id и код
C-…), вендор → его заявки и журнал, опубликованная витрина → сайт (`apps.web` + `/venue/:slug`) и
её заявки, видео предложения — ссылками наружу. Цвет плашки статуса — одна таблица
`toneOf(domain, status)` в `ui.tsx` (good — на сайте, одобрено; outline — ждёт; warn — отклонено,
заблокировано, просрочено; muted — черновик, снято, закрыто, отключено; strong — только
«Обложка»). Кнопки — токены набора (`.btn` как `.ui-btn`), одна главная на экран (`FormBar` —
главной, только когда есть что сохранять), подтверждение необратимого — залитая
`.btn-danger-fill` (к нему ведёт `.btn-danger` рамкой), занятая запросом — `aria-busy` и «…»
(`busyLabel`). Сделанное без видимого следа (снять услугу, обложка, одобрить фото, отметка
проверки) — всплывающей строкой (`useToast`; `ToastProvider` — в оболочке, над нижней панелью).
Витрина на телефоне — оглавление блоков (`SectionIndex`) перед ними, прилипает под шапкой;
«Опубликовать» и «Отправить на проверку», пока чего-то не хватает, — шторка перечисляет пункты,
кнопка недоступна. Журнал: объект — поиском по виду (`Combobox`: вендор, витрина, клиент, заявка,
сотрудник), «Сотрудник» — и отключённые, и только когда «Кто» — сотрудник. Проверки —
`e2e/admin/navigation.spec.ts` (оба проекта).

Модерация на телефоне — разбор подряд: вверху сводка очередей (число — кнопкой к очереди), у
заголовка очереди — число (всего, `total`; очередь — страницами по 20), пустая — строкой; фото и
услуги очереди открывают витрину на своём блоке (`?focus=`); у услуг и фото
витрины не на сайте — её статус; решение по услуге — в очереди (`ServiceDecision`, тот же — на
странице витрины), после него фокус на следующей услуге; после решения по предложению изменений или витрине на проверке —
`NextInQueue` («следующее в очереди» с фокусом, кончилась — «К модерации»). «Чего не хватает» на
странице витрины — у пункта «Перейти» к блоку, где он заполняется (`focusSection`: заголовок с
`tabIndex={-1}`), проверка вендора — одной строкой со ссылкой на вендора; у витрин на странице
вендора пунктов его проверки нет — они в «Проверке вендора». Слова — как в кабинете: витрина (не
«карточка»), предложение изменений (не «правка»), дополнения услуги.

Несохранённое: форма с вписанным, но не сохранённым отмечает себя `useUnsaved(dirty)`
(`apps/admin/src/unsaved.tsx`; `ConfirmForm` — сама). Уход с экрана — ссылка, нижняя панель,
«назад» браузера и Telegram (`useRoute` возвращает адрес в историю), выход — спрашивает
«Уйти без сохранения?»; перезагрузка — `beforeunload`, закрытие Mini App —
`enableClosingConfirmation`. Сохранили и уводим на результат — `navigate(view, { force: true })`.
Чужой роли раздел по ссылке — «нет доступа» без запроса; «Повторить» — только где повтор поможет
(`isRetryable`: нет связи, 5xx, 429). Код ошибки API без текста в `t.api` роняет `texts.test.ts`.
Полоса «нет связи» прилипает к верху ниже безопасных зон, шапка — под ней (`--net-h`).

### Кабинет партнёра: Mini App и сайт

Раскладку выбирает `apps/vendor/src/layout.ts` (те же границы — в `@media` `styles.css`): до

уже 390px месяц — от края до края (иначе день уже 44px). Ссылки на другие приложения, роль и
выход — раздел «Аккаунт». Вне Telegram без сессии — `Welcome.tsx`: что это за кабинет, как
получить доступ (кабинет открывает команда, бот привязывает номер), вход через хаб; без чисел.
Язык до входа: ссылки сайта на кабинет несут `?lang=` (`takeLangParam` в `lang.ts` — запомнить и
убрать из адреса), в хаб кабинет уводит с тем же `lang`; после входа — язык профиля.
Все разделы — свои части сборки (`screens.tsx`, без React.lazy: отказ загрузки куска —
«Повторить» и повтор при возврате связи): заявки — как только ясно, что вход будет (`warmInbox`,
параллельно с запросами входа), остальное — после входа; конфигурация категорий — тоже своим
куском (`CATEGORY_KIT`, подписи боковой панели — `usePart`), в основную часть её не тянуть; React —
отдельный кусок (`vite.config.ts`). Пока грузятся данные — заготовка формы содержимого
(`Loading kind`), а не строка «Загрузка…». `GET /auth/methods` — один на страницу (`hub.ts`), имя
бота — оттуда же. В Telegram — цвета шапки и фона из токенов, без сворачивания
свайпом (`announceReady`). Фокус после перехода — на заголовок экрана, и когда он появляется
позже (данные ещё грузятся). Проверки — `e2e/vendor` (проекты `vendor-phone` и
`vendor-desktop`, каждый экран на 320–1440px).

Витрина кабинета выбрана одна на все разделы (`listingId` в `App.tsx`): на компьютере — список
витрин в боковой панели (на входящих — с «Все витрины»; над списком второго выбора нет,
`SideVitrinas.tsx`), на телефоне и планшете — вверху календаря, витрины и услуг: две — две
пилюли во всю ширину, больше — список выбора `Select` (`ListingPicker.tsx`). Входящие — все
витрины или одна (`?listingId=`; значок у раздела — по всем); витрина не на сайте — строка «что
дальше» со ссылкой на её чек-лист готовности (`Venue.tsx`, `Readiness`: почему не опубликована,
пункты партнёра — с кнопкой туда, где их делают, одинаковые кнопки — одним пунктом, что сделает
команда — строкой; до публикации пункты — по `reviewBlockers`: что ждёт решения команды, уже не
пункт; всё сделано у черновика или отклонённой — «Отправить на проверку», потом «на проверке у
команды»; отправляет только владелец),
у заявки — категория, часть дня и «что нужно клиенту» (`detailRows`, `chosenServices`). «Услуги»
(`Services.tsx`): каталог категории, черновик и проверка, правка услуги на витрине — предложением,
удалить и снять — через подтверждение; сотрудник площадки только смотрит. Пять подписей нижней
панели уже 390px — кеглем 11, целиком и на 320px. Изменения витрины — предложением: название,
описания, данные витрины из конфигурации (`Attributes.tsx`) и ссылки на видео; цены — только в
услугах (на витрине — цена «от» и ссылка на «Услуги», списка услуг второй раз нет). Фото
портфолио — «люди согласны» (`X-Photo-Consent`) или «лиц нет». Календарь — по режиму: day и slot —
дни, parts — день открывается частями (строки с переключателем «занято», на телефоне день
прокручивается к ним), заказов одновременно — правкой с If-Match, lead — срок заказа без
календаря. Каждое объяснение — один раз на экран. Ошибка API — словами по коду (`errors.ts`,
`err_<код>` в словаре; код без текста роняет `i18n.test.ts`), «Повторить» — только где поможет.
Несохранённое — как в панели (`unsaved.tsx`: форма услуги, предложение, причина отказа, заказов
одновременно; уход, смена витрины, «назад» браузера и Telegram — «Уйти без сохранения?»). Что ждёт

последнее предложение; считается запросом, у сотрудника площадки — нули): значки у «Витрины» и
«Услуг», как у входящих; причина отказа — у фото, история решений по предложениям — по кнопке; «первым
ответил менеджер Bayramm» — у заявки, где `firstResponseBy` = staff. Подмена
API в e2e: `listings: "many"` — зал, кортеж, фото и видео, торты.

### Клиент: маршруты, раскладка, лендинг

Маршруты — одна карта `apps/web/src/routes.ts` (без React: её читает и воркер). Корень `/`
в браузере — лендинг, внутри Telegram — каталог (`screenOf`); каталог — `/catalog`, документы —
`/docs`. Старые ссылки `/?category=…&date=…&guests=…` (так их собирает бот) в браузере уводят в
`/catalog` с теми же фильтрами (`normalizeStartUrl` в `bootstrap.ts`), `?lang=ru|uz` —
выбор языка, из адреса убирается. Экраны — ленивые куски (`src/screens.ts`), тесты jsdom
грузят их заранее (`src/test-setup.ts`).

Категории в клиенте строятся из `@bayramm/shared/categories`, а не пишутся под каждую
(`src/categories.ts`; коды категорий маршрутов — `CATEGORY_CODES` в `routes.ts`, сверяет тест).
Каталог — `/catalog?category=<код>`; без параметра — «Все» (витрины всех включённых категорий
вперемешку, у API `category=all`; карточка подписывает раздел): переключатель — «Все» и категории с
витринами (`GET /catalog/categories`). Фильтры — одной строкой пилюль (`.filter-row`: на телефоне и
планшете — лента с прокруткой вбок, с 1024px — переносится; выбранный — залит, как раздел): место,
дата, гости, «Ещё фильтры», сортировка. Место — один список «город → район»
(`screens/catalog-place.ts`): весь город (`?city=` — его районы и выездные витрины без района) или
один район (`?district=`, город не пишется); пока город один, «Ташкент — весь город» — значение по
умолчанию, районы — под ним с отступом (`nested` у `Select`); города — `app.cities`, район знает
город (`app.districts.city_code`), справочник — `cities` и `districts[].city` в `GET /dictionaries`.
Место — во всех разделах и у «Всех»; гости — только где вместимость (залы); поля витрины — только в
разделе: `?a.<поле>=` из `categoryFilters` (`screens/catalog-filters.ts`; колонка слева на
компьютере, шторка по «Ещё фильтры» на телефоне и планшете), отметки на дату — «свободно / частично занято / занято» (у
`lead` — нет), цена — с единицей (`unitText` в `format.ts`). Витрина — услуги с единицами,
минимумом, сроком и опциями (кнопка «в заявку» кладёт услугу в черновик формы), поля витрины
(`screens/venue-attributes.ts`), видео — только ссылками наружу (`normalizeVideoLink`, без
встраивания), занятость по модели: `parts` — календарь с частично занятыми днями (`partial` у
`Calendar` набора) и утро / день / вечер на дату, `lead` — срок заказа вместо календаря; день,
выбранный в календаре витрины, — в её адресе (`?date=`) и оттуда в форме заявки. Форма
заявки — поля `requestForm` категории (гости — required / optional / hidden; hidden не
передаётся), услуги с количеством и опциями и примерной суммой (`screens/request-estimate.ts`,
подписана как предварительная); проверка — `validateRequestDetails` плюс срок заказа, занятая
часть дня и минимум услуги (`screens/request-draft.ts`); `date_busy` от сервера — ошибка у даты, и
день в календаре формы занят. Дата из фильтра занята — на витрине блок `BusyDay`: ближайшие
свободные дни (`nearbyFreeDays`) и «кто свободен в эту дату», кнопка — «Заявка на другую дату»
(в форму без даты); пришли в форму с занятой датой — подсказка у поля. Гостю сайта пометка над
кнопкой заявки заранее говорит, что отправить её можно после входа (телефон — если `phone: true`);
экран заявки гостя показывает, что уже выбрано (дата, гости, услуги — после входа на сайте в этой
вкладке они в форме). Демо-API (`VITE_API=mock`) — 24 зала и по
три витрины в каждой включённой категории (`api/demo-vitrinas.ts`); `LISTINGS` в тестах — залы,
`allDemoListings` — все. Публичные ответы API (категории, выдача, витрина, бот, тексты согласий)
идут через кэш вкладки (`api/cache.ts`, `withCache` в `bootstrap.ts`): один запрос на всех, `peek` —
экран сразу с данными. Выдача каталога хранит снимок (`catalog-feed.ts`), router — прокрутку у
записи истории: «назад» из витрины (и кнопка Telegram) — та же выдача на том же месте. Карточка
грузит витрину заранее по наведению или касанию, витрина — форму заявки; загруженный кусок экрана
рисуется без `React.lazy` (`screens.ts`). Страница каталога категории — своя для поисковиков (title, canonical с
`?category=`, у залов тоже; sitemap — «Все», категории с витринами и витрины всех категорий).

Оболочка — у гостя и после входа разная (`apps/web/src/nav.ts`). Гость в браузере — сайт:
шапка с логотипом, языком (в шапке с 390px, на внутренних экранах — с 768px; всегда — в меню и
подвале), «Войти» и меню-шторкой (`components/SiteMenu.tsx`: каталог, сохранённое, документы,
бот, язык, вход); нижней панели нет, на компьютере в шапке — каталог и сохранённое. Разделы в шапке
компьютера (`.site-nav`) — кнопки-пилюли с иконкой, текущий — залит. «Мои
заявки» и профиль гостю не показываются: сразу хаб с возвратом сюда (`signInGate`). После входа
и всегда в Telegram — оболочка приложения: четыре вкладки внизу, на компьютере — в шапке.
Пререндер лендинга — оболочка гостя (вошедший видит её до первой отрисовки).

Раскладку решает ширина экрана, и в Telegram тоже: до 767px — телефон (нижняя панель после
входа, панели действий у низа), 768–1023px — колонка 720px по центру, от 1024px — шапка с
разделами (у гостя и «Войти»), без нижней панели; ширина содержимого — `widthOf` (`wide` 1280 ·
`text` 720 · `form` 640). Каталог — 3 колонки, с 1280px — 4; с колонкой фильтров слева — 2 и 3
(`CARD_PHOTO_SIZES` в `ListingCard.tsx` — те же ширины для `srcset`); площадка — фото и описание слева, справа прилипает карточка с
ценой, телефоном и заявкой. Подвал — только у сайта; язык в нём — строкой «Язык: Русский ·
Oʻzbekcha» (переключатель — в шапке и меню). Пустая выдача с фильтрами называет, что её
ограничивает (место, гости, поля витрины; дата не отсекает), — каждый убирается кнопкой. Лендинг (`screens/Landing.tsx`) — про
весь праздник, каждое — один раз: подбор (что ищете, дата, гости — у залов), разделы одной
сеткой (пустой — «скоро», чисел нет), по витрине из разных разделов из `GET /catalog/listings`
(нет — блока нет), шаги, обещания — из правил продукта, вопросы — о том, чего выше нет. Уведомление «Сохранили» говорит, где список: у приложения —
вкладка, у гостя сайта — раздел вверху страницы.

Разметку для поисковиков и превью ссылок ставит воркер (`apps/web/worker/meta.ts`, `seo.ts`):
title, description, canonical, hreflang (`?lang=`), Open Graph (`public/og.png`, у площадки —
обложка), `<noscript>`; неизвестный путь и снятая площадка — 404. `robots.txt` и
`sitemap.xml` (площадки — из API, кэш на час) — тоже воркер; индексируется только
`bayramm.uz`, staging — `noindex` и `Disallow: /`.

Лендинг пререндерится при сборке (`apps/web/vite-prerender.ts` → `src/prerender.tsx`,
`react-dom/server` в Node): в `index.html` — `<template data-prerender="ru|uz">`, воркер
(`worker/prerender.ts`) убирает их со всех страниц и на `/` кладёт вариант языка страницы в
`#root` — до JS и без него виден лендинг (залы — заготовки, придут после JS). Приложение не
гидрирует, а заменяет его первой отрисовкой (`createRoot`); экран лендинга `bootstrap`
грузит до неё (`loadStartScreen`), поэтому без заглушки. `public/boot.js` (обычный скрипт в
`<head>`, CSP) ставит `<html data-boot="skip">`, если приложение покажет другое — Mini App
(там корень — каталог) или другой язык, — и `public/boot.css` прячет пререндер; его правила
обязаны совпадать с `getWebApp`/`launchedFromTelegram` и `initialLang` (`src/boot.test.ts`).
Ещё он просит заранее (modulepreload) словарь своего языка и экран первого показа — адреса
вписывает сборка. Портал в разметке пререндера невозможен: `Shell` с `prerender` — без
уведомлений и избранного. Словари клиент грузит по языку (`src/i18n.ts`): первый — до
первой отрисовки, второй — при переключении (заранее — при наведении на переключатель);
поэтому у `@bayramm/shared` `sideEffects: false`. Воркеру словари нужны оба — у него своя сборка.

### Иконки и узор

Иконки — **Phosphor**, вшиты как inline SVG: duotone для смысловых, bold для
управляющих, fill для активных состояний. В прототипе 68 штук, мёртвых нет —
проверяется тестом.

Фирменный мотив — **восьмиконечная звезда гириха** (отсылка к Регистану).
Повторяющийся фон из data-URI, плитка 52px на карточках и 84px на крупных
поверхностях, обводка в цвет линейки. Только за иллюстрациями и в пустых
состояниях, **никогда за текстом**.

> В data-URI символ `#` обязан быть записан как `%23`, иначе браузер обрежет
> строку на нём и фон не появится. Обжигались.

### Контраст

`--coral` — только заливки, иконки и крупный текст (3:1). Для кнопок с белым
текстом и текста мельче 18px — `--coral-deep` (белый на нём 5,36:1).

Пары «текст/фон» объявлены в `packages/ui/src/pairs.ts`; тест проверяет каждую
в обеих темах: мелкий текст ≥ 4,5:1, крупный и иконки ≥ 3:1. Новый цвет или
новая пара — сначала в `pairs.ts`, потом в интерфейс.

В прототипах контраст меряет `pnpm audit` (с учётом прозрачности и наследования).

### Фото

Один оригинал на фото, варианты — на лету. Всё из `packages/media`:

- **браузер** — `compressForUpload` (`@bayramm/media/browser`): ориентация из
  EXIF, длинная сторона ≤ 2560, WebP 0.9 (где WebP не кодируется — JPEG 0.9),
  метаданные вырезаны. Перекодирование всегда — так GPS не уходит с телефона;
- **сервер** — `assertUploadable` по байтам, клиенту не верим: WebP/JPEG/PNG,
  ≤ 10 МБ, размеры, никаких EXIF/XMP. Кладёт в Storage только API ключом
  service_role; ключ объекта `listings/<листинг>/<uuid>.<расширение>`;
- **выдача** — `mediaUrl` / `mediaSrcSet`, ширины 320·640·960·1280·1920 и
  никаких других: каждая новая — уникальные преобразования в квоте Cloudflare.

### Telegram

Каждый вызов SDK защищать проверкой наличия метода — приложение обязано
работать в обычном браузере и в старом клиенте.

Безопасные зоны: значение Telegram → системное `env()` → ноль. Верхний
отступ складывает **обе** зоны — вырез устройства плюс кнопки Telegram. Без
второго слагаемого содержимое лезет между кнопками клиента.

`initData` проверять **на сервере** по подписи. Без этого любой может
представиться любым пользователем.

## Ловушки

На этом уже обожглись. Не повторять.

1. **Атрибуты `data-*` не должны пересекаться.** Календарь использовал
   `data-pick` для дней, триггер выпадающего списка назвали так же —
   обработчик стал перехватывать клики по датам, дата молча перестала
   выбираться.

2. **`overflow-y:auto` без `overflow-x`** делает горизонталь прокручиваемой
   по спецификации. Слой уезжает вбок и не возвращается.

3. **`focus()` на элементе, который ещё едет**, заставляет браузер
   прокрутить контейнер, и тот остаётся сдвинутым. Решение: `overflow:clip`
   на корпусе, `focus({preventScroll:true})`, фокус после окончания перехода.

4. **`100dvh` без запасного `100vh`** — в браузерах без поддержки корпус
   теряет высоту, нижняя панель уезжает за экран.

5. **`matchMedia`, `scrollTo`, `AudioContext` есть не везде.** В старых
   вебвью Android их может не быть.

6. **Правило только на `:hover` на телефоне недоступно.** Кнопка, показанная
   по наведению, для пальца не существует.

7. **Переопределения класть после того, что они переопределяют.** Иначе
   каскад держится только на весе селектора.

8. **Позиционирование легко сбить списком селекторов.** Кнопка была
   `absolute` в правом верхнем углу; попала в общий список с
   `position:relative` для расширения зоны нажатия — уехала в левый нижний
   угол потока.

9. **Номера экранов и вкладок держать в одной карте.** Вписанные числом, они
   разъехались трижды: кнопка после заявки уводила не туда, сердечко
   перестало обновлять список.

10. **Лишняя закрывающая скобка в CSS.** Браузеры прощают, строгий разбор —
    нет. Проверять баланс автоматически.

## Персональные данные

Собираем о клиенте: Telegram ID, имя, телефон, дата события, гости, бюджет,
комментарий. Только по раздельному согласию, **с журналом**: что, когда,
версия текста, возможность отзыва.

О вендоре: название, категория, район, фото без лиц, телефон, ФИО контактного
лица, СТИР, адрес, отметку о проверке.

**Не собираем:** паспорт и сканы, ПИНФЛ, дату рождения, фото лица, точную
геолокацию.

СТИР сверяется с открытым реестром, **скан не храним** — храним отметку о
проверке.

Вендор видит о клиенте ровно то, на что тот дал согласие. Выгрузка базы
клиентов недоступна ни в каком виде.

В коде API схема `pii` (таблицы и функции `read_*`) упоминается только в
`apps/api/src/db/pii.ts`: новое чтение или запись ПДн — правка этого модуля.
Упоминание в любом другом файле `src` роняет тест `db/pii.test.ts`.

Журнал действий, журнал доступа к ПДн и недоставленные уведомления в панели — с подписями объектов
и людей (витрина, вендор, заявка №, клиент `C-…`, сотрудник, партнёр; `apps/api/src/staff/labels.ts`,
имена — через `db/pii.ts`), без телефонов; список заявок — с именем, которое клиент указал в заявке.
