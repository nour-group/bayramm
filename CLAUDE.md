# Bayramm

Площадка поиска подрядчиков на праздники в Ташкенте. Telegram Mini App плюс
сайт. Русский и узбекский.

> **Репозиторий публичный.** Спецификации, аудит, планы, юридические и
> бизнес-детали живут в приватном `nour-group/bayramm-internal`, локально —
> в `internal/` (в `.gitignore`). Ничего оттуда не копировать сюда: ни в код,
> ни в комментарии, ни в описания PR и issue. Если папка есть — прочитай
> её `CLAUDE.md`:
>
> @internal/CLAUDE.md

В репозитории — приложения, общий код, миграции и три прототипа
интерфейса (клиент, кабинет вендора, админка).

---

## Монорепо

```
apps/web          клиент: Telegram Mini App + сайт (Vite + React) → Cloudflare Workers (static assets)
apps/vendor       кабинет вендора (Vite + React) → Cloudflare Workers (static assets)
apps/admin        панель оператора (Vite + React) → Workers; вход — хаб на сайте или Mini App из бота
apps/api          сервер (Hono) → Cloudflare Workers
apps/media        варианты фото: /<ширина>/<ключ> → Supabase Storage через Image Transformations
supabase/         миграции и сид Postgres (Supabase)
packages/edge     воркер статических приложений: /api → API, SPA, заголовки безопасности
packages/media    фото: сжатие в браузере, проверка байтов на сервере, ключи и адреса вариантов
packages/tg       Telegram: проверка initData и виджета входа, deep links startapp, секрет вебхука
packages/shared   словари RU/UZ (типизированные), normalizeUz
packages/ui       дизайн-токены (tokens.ts → tokens.css), две темы, тест контраста, свои шрифты (fonts.css);
                  свои контролы на React вместо системных (@bayramm/ui/react + kit.css)
prototypes/       client · vendor · admin — спецификация, не основа кода
e2e/              сквозные проверки в браузере (Playwright + axe): правила продукта, доступность
internal/         приватные документы (клон bayramm-internal, в .gitignore)
```

Пакетный менеджер — **pnpm** (workspaces). Линтер и форматтер — **Biome**.

```bash
pnpm install
pnpm dev:web          # клиент локально
pnpm dev:vendor       # кабинет вендора локально
pnpm dev:admin        # панель оператора локально
pnpm dev:api          # API локально (wrangler dev)
pnpm lint             # biome check
pnpm typecheck        # tsc по всем apps/* и packages/*
pnpm test             # тесты пакетов, приложений и всех трёх прототипов
pnpm e2e              # сквозные в Chromium (один раз: pnpm --filter @bayramm/e2e e2e:install)
```

Окружения: `local` (по умолчанию), `staging`, `production` — блоки `env` в
`wrangler.jsonc` каждого приложения. Секреты — только `wrangler secret put` и
`.dev.vars` (в `.gitignore`), никогда не в репозитории.

Воркеры web, vendor и admin собраны на `createSiteWorker` из `packages/edge`:
`/api/*` уходит в API по сервисной привязке без префикса, остальное — статика с
CSP и прочими заголовками безопасности. CSP пускает только свой origin и не
допускает встроенных скриптов и стилей; нужен внешний источник (шрифт,
`telegram-web-app.js`) — добавить его в `security-headers.ts` явно. Фото с воркера
media — параметр `imageOrigins: mediaImageOrigins(dev)` (только чистый origin). Так сделано
для виджета входа Telegram: опция `telegramLoginPaths` пускает его скрипт и фрейм
`oauth.telegram.org` только на этих путях — у сайта это хаб `/auth`, больше нигде. Колбэк
`data-onauth` виджет исполняет через `eval`, поэтому хаб берёт данные через редирект
`data-auth-url` (`/auth/telegram`). Панель — ещё и Mini App: `telegramWebApp` и
`frameAncestors: ["https://web.telegram.org"]`.

### Аккаунт: один на все роли

Человек — одна запись `app.accounts`; способы входа — `app.account_identities`
(`telegram` и `phone`, значение — HMAC от `ID_HASH_KEY`, у каждого способа один
владелец); клиент, партнёр вендора (`app.vendor_users`) и сотрудник (`app.staff`) — роли
с `account_id`. Имя из Telegram — `pii.account_profiles`. Слияния аккаунтов нет: способ,
который уже у другого аккаунта, не добавляется (`identity_taken`). Сессия (`app.sessions`)
всегда принадлежит аккаунту: `kind` account — 7 дней, staff — 12 часов и только по
входу не старше 12 часов (`proof_at`); отключение сотрудника или аккаунта отзывает сессии.

Входы (`apps/api/src/routes/auth.ts`): initData Mini App (`POST /auth/telegram`, кабинет —
с `app: "vendor"`), виджет на хабе (`POST /auth/widget`), код по телефону
(`POST /auth/phone/send` → `/verify`: 3 кода за 10 минут на номер и на IP, 5 попыток,
код живёт 10 минут, повтор через 60 секунд, хранится HMAC). Отправитель кода —
`OTP_PROVIDER`: `off` (вход по телефону выключен), `console` (только `APP_ENV=local`),
`tg_gateway` (Telegram Gateway, секрет `TELEGRAM_GATEWAY_TOKEN`). `GET /auth/methods` —
чем можно войти и адреса приложений; `GET /me` — аккаунт, способы входа и роли. Тексты входа
(хаб, профиль, кабинет, панель) упоминают телефон, только если `phone: true`. Старые
`/auth/vendor/telegram` и `/auth/staff/telegram` приложения не вызывают: они устарели, остаются
для старых сборок и пишут каждое обращение в лог (`auth.legacy`) — удалить, когда обращений нет.

Кабинет и панель вне Telegram входят через хаб на сайте (`apps/web/src/screens/SignIn.tsx`):
уводят браузер на `<сайт>/auth?app=…&state=…&challenge=…` (PKCE S256,
`@bayramm/shared/pkce`), хаб после входа берёт одноразовый код (`POST /auth/hub/code`:
60 секунд, один раз, привязан к приложению, его origin, state и challenge) и уводит на
`<приложение>/auth/callback`; приложение меняет код + verifier на свою сессию
(`POST /auth/hub/exchange`). Общих cookie между поддоменами нет. Панель затем повышает
сессию аккаунта до сессии сотрудника (`POST /auth/staff/elevate`) и сразу отзывает
первую; в Telegram — `POST /auth/staff/webapp` по initData. Ссылка с `?signin=1` из
другого приложения сразу уводит в хаб; внутри Telegram ссылки на другие роли идут через
бота (`?start=cabinet|admin`, `?startapp`). Партнёр нескольких вендоров выбирает кабинет:
заголовок `X-Bayramm-Vendor` (без него — 409 `vendor_choice_required`).

Сотрудники входят по приглашению: запись в `app.staff` с
`pii.staff_profiles.telegram_username` или `app.staff.phone_hash`; приглашение принимает первый
вход аккаунта с этим Telegram или номером — оно привязывается к аккаунту. По телефону
приглашают из «Команды» (`app.staff_invite_phone`, через `apps/api/src/db/pii.ts`): хранится
только HMAC номера; номер, уже подтверждённый у аккаунта, принимает приглашение сразу. Так же его
принимает первое сообщение боту (имя пользователя — из подписанного обновления).
`/start` показывает кнопку каждой роли аккаунта (панель, кабинет, приложение) на языке,
сохранённом в профиле, иначе — на языке Telegram; сотруднику — карточку команды, `/stats`
и `/admin`. Приглашает, меняет роль и отключает администратор в разделе «Команда»
(функции `app.staff_invite`, `app.staff_set_role`, `app.staff_set_active`): себя — нельзя,
последнего действующего администратора база не отключит и не понизит никаким путём.
Виджет входа работает на одном домене бота: у бота каждого окружения в @BotFather
`/setdomain` — домен сайта этого окружения, тот же в `TELEGRAM_LOGIN_DOMAIN` API.

Имя бота нигде не вписано: у каждого окружения свой бот, API узнаёт его по
токену (`getMe`, кэш на час) и отдаёт в `GET /api/telegram/bot` вместе с
адресом Mini App (`WEB_APP_URL`), а также в `GET /api/auth/methods`; приложения берут
имя оттуда. Команды, описания и
кнопку меню задаёт код — `apps/api/src/telegram/bot-profile.ts`; деплой
применяет его через `POST /telegram/sync` (секрет `TELEGRAM_SYNC_KEY` в воркере
API и в GitHub Environment). В @BotFather вручную — только `/setdomain` и
основное Mini App.

Бот принимает сообщения вебхуком `POST /telegram/webhook` (его ставит тот же
`/telegram/sync` на `API_URL`; секрет выводится из `ID_HASH_KEY`). Вендор
привязывает Telegram, поделившись своим контактом: номер сверяется с
`app.vendor_users.phone_hash` = HMAC(`ID_HASH_KEY`, «+998XXXXXXXXX») —
`phoneHash` в `apps/api/src/auth/crypto.ts`, привязка — `app.vendor_user_claim_telegram`
(номер уникален внутри вендора: один человек бывает партнёром нескольких). Вход аккаунта
с этим номером по коду привязывает к нему все такие записи.
Кабинет вендора — `VENDOR_APP_URL`. Карточку партнёр меняет предложением правки
(`/vendor/listings/:id/revisions` → `app.listing_revisions`: название, цена, описания, пакеты;
одна открытая на площадку, в правке только изменённые поля), решает команда в «Модерации»;
клиент до решения видит прежнюю карточку. Уведомления ставят в `app.outbox` триггеры
базы (в payload только id), отправляет cron API раз в минуту; маршрут, после
которого ждать минуту не хочется, вешает `outboxKick`
(`apps/api/src/notify/kick.ts`). SLA 12 часов — там же, по cron. «Связались», отмеченное
сотрудником (`first_response_by = staff`), клиенту — не «площадка ответила», а «команда
связалась с площадкой»; новая правка карточки — `ops.revision_submitted` тем, кто решает по правкам.

Лимиты частоты — привязки Workers Rate Limiting (`ratelimits` в
`apps/api/wrangler.jsonc`, `apps/api/src/ratelimit.ts`): `POST /auth/*` по
HMAC от IP, `POST /requests` по IP и по клиенту; превышение — 429
`rate_limited` с `Retry-After`. Привязки не наследуются окружениями, у каждого
окружения свои `namespace_id` (проверяет `config.test.ts`).

Сроки хранения и истечение заявок — `app.run_daily_maintenance()` (раз в день
по Ташкенту, повтор в тот же день ничего не делает); запускает его шаг
`daily_maintenance` того же cron в окне 21:00–21:59 UTC
(`apps/api/src/maintenance`). Отдельный Cron Trigger не заводить — их мало на
бесплатном тарифе. Права клиента на свои данные — `GET /me/export`,
`POST /me/consents/withdraw`, `DELETE /me` (функции `app.client_*`, только над
собой). Доступность staging и production каждые 15 минут проверяет workflow
`Uptime`.

Метрики запуска («заявка → ответ площадки за 12 часов») считает только база:
факты заявки — представление `app.request_metric_facts`, суммы — функции
`app.metrics_*` (миграция `20260930220000_launch_metrics.sql`, там же определения).
Ответ площадки — её первый переход в contacted/deal/declined по
`app.request_status_log`; «связались» от сотрудника, просмотр и звонок — не ответ.
Панель — раздел «Метрики» и блок на странице вендора (`/staff/metrics`, право
`metrics.read`); те же функции собирают отчёты бота администраторам: сводка каждое
утро и недельный по понедельникам (`app.enqueue_ops_reports`, шаг `ops_reports`
cron в окне 04:00–04:59 UTC, один раз за день и неделю). Ответ API 5xx —
`app.record_api_error` из `app.onError` после ответа: оповещение `ops.api_error` не
чаще раза в 30 минут, только метод и шаблон маршрута. Пауза между напоминаниями
вендору от сотрудника — настройка `ops_reminder_pause_minutes`
(`app.ops_reminder_pause()`). Workers Logs включены у всех воркеров
(`observability`; у клиента — каждый десятый запрос).

## Что делать в первую очередь

Первый запуск — **одна категория, залы Ташкента, 30–50 штук**. Цель не
«сделать платформу», а доказать: клиент отправляет заявку, вендор отвечает
за 12 часов.

Порядок:

1. Инфраструктура, схема БД, аутентификация
2. Кабинет вендора: вход, карточка, календарь, заявки
3. Заявка end-to-end: запись в БД, уведомление вендору в Telegram, статусы
4. Клиентское приложение на реальных данных вместо вписанных
5. Админка: модерация вендоров

Не начинать с премиума, рекламы, подписок, статистики и остальных семи
категорий. Они во вторую очередь.

## Правила продукта — нарушать нельзя

Они не про стиль, а про суть продукта. Каждое проверяется тестами в
`prototypes/client/smoke.js`, на живом клиенте — `e2e/web/rules.spec.ts`.

| Правило | Что это значит в коде |
|---|---|
| Клиент не платит | Ни комиссий, ни платы за заявку. Деньги через нас не идут |
| Заявка, не бронь | Слово «забронировать» запрещено в интерфейсе и словарях |
| Телефон виден сразу | Номер вендора отдаётся до отправки заявки, не после |
| Цена обязательна | Вендор без цены не публикуется. «По запросу» не допускается |
| Фото обязательны | Минимум 3. Без фото карточка не публикуется |
| Реклама помечена | Каждый оплаченный блок несёт слово «Реклама» |
| Согласие не предзаполнено | Раздельно по целям, кнопка отказа того же размера |
| Место в выдаче не продаётся | Оплата не влияет на сортировку по цене и рейтингу |
| 12 часов на ответ | Не ответил — клиенту показываются похожие |

Последнее — обязательство, данное клиенту в интерфейсе. На сервере нужен
счётчик и эскалация.

## Чего в прототипе нет и что надо заменить

| В прототипе | В продакшене |
|---|---|
| 84 вендора вписаны в код | Таблица, админ-CRUD, модерация |
| Занятость из формулы `(ключ×7 + seed×13) % 9 < 2` | Календарь, который ведёт вендор |
| `reqs.push({...})` в память вкладки | Запись в БД, уведомление вендору, статусы |
| Статусы из `seed % 3` | Машина состояний с историей |
| Фото в base64 внутри HTML | Объектное хранилище, CDN, ресайз, снятие EXIF |
| `TODAY = new Date(...)` | Системное время, часовой пояс Ташкента |
| Язык и избранное в памяти | Профиль пользователя в БД |
| Премиум-флаг вписан в код | Присвоение админом после выездной проверки |
| Шрифты с Google Fonts | Локальный хостинг |

**Рейтинги и число отзывов у всех 84 вендоров выдуманы.** Показывать их
живым людям нельзя. На первом запуске рейтинг убрать или заменить значком
«Новый на площадке».

## Прототип — спецификация, а не основа кода

`prototypes/client/index.html` — один файл на 859 КБ: 739 КБ логики и 569 КБ картинок
в base64. **Переносить его как есть не нужно.**

Брать из него: правила, тексты на двух языках, палитру, шкалы, раскладку,
сценарии экранов, поведение календаря и формы заявки.

Он запускается двойным щелчком и работает целиком — это быстрее, чем читать
описание.

```bash
cd prototypes/client

cd prototypes/admin  && pnpm test   # дымовые тесты панели оператора
```

`pnpm test` проверяет не только вёрстку. Если убрать телефон вендора за форму
заявки или позволить оплате влиять на сортировку по цене — тест упадёт.

При изменении интерфейса продакшена стоит перенести эти проверки туда же.

`pnpm e2e` поднимает три сервера разработки и гоняет их в Chromium на 390×844 и
1280×800 без сети: у клиента демо-API (`VITE_API=mock`), у кабинета и панели `/api`
перехватывает тест (`e2e/support/`), Telegram — поддельный `WebApp`. На каждом
главном экране — axe (WCAG 2.2 AA, серьёзные и критичные нарушения), видимый фокус,
зона нажатия 44px, без горизонтальной прокрутки. Осознанное исключение из контраста —
сначала в `EXEMPT_PAIRS` (`packages/ui/src/pairs.ts`), потом в `e2e/support/a11y.ts`.

## Соглашения

### Двуязычность

Словари — в `packages/shared/src/i18n` (`ru.ts`, `uz.ts`). Тип `Dict`
выводится из `ru`, `uz` обязан ему соответствовать — лишний или пропущенный
ключ не компилируется. В строках нет HTML: богатый текст — структурные блоки.

Узбекский — латиница. Апострофы: `ʻ` (U+02BB) после o/g — `oʻ`, `gʻ`;
`ʼ` (U+02BC) — tutuq belgisi. Прямые и кавычки-апострофы запрещены тестом;
для поиска — `normalizeUz()`. *Соглашение ждёт подтверждения владельцем текстов.*

### Дизайн-система

Источник правды — `packages/ui/src/tokens.ts`; `tokens.css` генерируется из
него (`pnpm --filter @bayramm/ui css`). Две темы: основная и премиум («Suzani»).

**Тема обязана переопределять базовые токены, а не отдельные классы.** Иначе
любое правило с `--muted` или `--coral` остаётся от светлой темы, и дыры
находятся бесконечно.

Шкалы: кегли 10–27 из фиксированного набора, скругления 3·8·11·14·18·22·999,
зазоры 3·5·7·9·12, отступы только чётные, иконки 12·14·17·20·24·26.

Зона нажатия минимум 44px — расширять невидимым слоем, не увеличивая рисунок.

### Контролы — только свои

Системные `<select>`, `<input type="checkbox|radio|number|date|file|search">`,
`<dialog>`, `window.confirm/alert/prompt` и подсказки `title=` в приложениях не
используются: в Telegram и старых вебвью они выглядят чужими, а список и календарь
не знают про безопасные зоны. Вместо них — `@bayramm/ui/react`: `Select`,
`Checkbox`, `Switch`, `RadioGroup`, `NumberStepper`, `DateField`/`Calendar`,
`FileDrop`, `SearchField`, `ConfirmSheet`/`Dialog`, `useToast`, `Tooltip`; стили —
`@bayramm/ui/kit.css` (подключать между `tokens.css` и стилями приложения). Под
рисунком галочек, радиокнопок и выбора файлов — настоящий `<input>`. Список и
календарь на телефоне — шторка снизу, на компьютере — панель у поля; страница под
ними inert. Слов в наборе нет: «Закрыть»/«Очистить» — `UiTextsProvider` в корне
приложения, остальное — пропсами. Страж — `packages/ui/src/react/native-controls.test.ts`.

### Иконки и узор

Иконки — **Phosphor**, вшиты как inline SVG: duotone для смысловых, bold для
управляющих, fill для активных состояний. В прототипе 68 штук, мёртвых нет —
проверяется тестом.

Фирменный мотив — **восьмиконечная звезда гириха** (отсылка к Регистану).
Повторяющийся фон из data-URI, плитка 52px на карточках и 84px на крупных
поверхностях, обводка в цвет линейки. Только за иллюстрациями и в пустых
состояниях, **никогда за текстом**.

> В data-URI символ `#` обязан быть записан как `%23`, иначе браузер обрежет
> строку на нём и фон не появится. Обжигались.

### Контраст

`--coral` — только заливки, иконки и крупный текст (3:1). Для кнопок с белым
текстом и текста мельче 18px — `--coral-deep` (белый на нём 5,36:1).

Пары «текст/фон» объявлены в `packages/ui/src/pairs.ts`; тест проверяет каждую
в обеих темах: мелкий текст ≥ 4,5:1, крупный и иконки ≥ 3:1. Новый цвет или
новая пара — сначала в `pairs.ts`, потом в интерфейс.

В прототипах контраст меряет `pnpm audit` (с учётом прозрачности и наследования).

### Фото

Один оригинал на фото, варианты — на лету. Всё из `packages/media`:

- **браузер** — `compressForUpload` (`@bayramm/media/browser`): ориентация из
  EXIF, длинная сторона ≤ 2560, WebP 0.9 (где WebP не кодируется — JPEG 0.9),
  метаданные вырезаны. Перекодирование всегда — так GPS не уходит с телефона;
- **сервер** — `assertUploadable` по байтам, клиенту не верим: WebP/JPEG/PNG,
  ≤ 10 МБ, размеры, никаких EXIF/XMP. Кладёт в Storage только API ключом
  service_role; ключ объекта `listings/<листинг>/<uuid>.<расширение>`;
- **выдача** — `mediaUrl` / `mediaSrcSet`, ширины 320·640·960·1280·1920 и
  никаких других: каждая новая — уникальные преобразования в квоте Cloudflare.

### Разметка и код из строк

Запрещены: `dangerouslySetInnerHTML`, `eval` (правила Biome), присваивание
`innerHTML`/`outerHTML`, `insertAdjacentHTML`, `document.write`, `new Function`
(плагин `biome/no-unsafe-sinks.grit`, исходники `apps/*` и `packages/*` без
тестов). Текст — `textContent` и JSX, богатый текст — структурные блоки.

### Telegram

Каждый вызов SDK защищать проверкой наличия метода — приложение обязано
работать в обычном браузере и в старом клиенте.

Безопасные зоны: значение Telegram → системное `env()` → ноль. Верхний
отступ складывает **обе** зоны — вырез устройства плюс кнопки Telegram. Без
второго слагаемого содержимое лезет между кнопками клиента.

`initData` проверять **на сервере** по подписи. Без этого любой может
представиться любым пользователем.

## Ловушки

На этом уже обожглись. Не повторять.

1. **Атрибуты `data-*` не должны пересекаться.** Календарь использовал
   `data-pick` для дней, триггер выпадающего списка назвали так же —
   обработчик стал перехватывать клики по датам, дата молча перестала
   выбираться.

2. **`overflow-y:auto` без `overflow-x`** делает горизонталь прокручиваемой
   по спецификации. Слой уезжает вбок и не возвращается.

3. **`focus()` на элементе, который ещё едет**, заставляет браузер
   прокрутить контейнер, и тот остаётся сдвинутым. Решение: `overflow:clip`
   на корпусе, `focus({preventScroll:true})`, фокус после окончания перехода.

4. **`100dvh` без запасного `100vh`** — в браузерах без поддержки корпус
   теряет высоту, нижняя панель уезжает за экран.

5. **`matchMedia`, `scrollTo`, `AudioContext` есть не везде.** В старых
   вебвью Android их может не быть.

6. **Правило только на `:hover` на телефоне недоступно.** Кнопка, показанная
   по наведению, для пальца не существует.

7. **Переопределения класть после того, что они переопределяют.** Иначе
   каскад держится только на весе селектора.

8. **Позиционирование легко сбить списком селекторов.** Кнопка была
   `absolute` в правом верхнем углу; попала в общий список с
   `position:relative` для расширения зоны нажатия — уехала в левый нижний
   угол потока.

9. **Номера экранов и вкладок держать в одной карте.** Вписанные числом, они
   разъехались трижды: кнопка после заявки уводила не туда, сердечко
   перестало обновлять список.

10. **Лишняя закрывающая скобка в CSS.** Браузеры прощают, строгий разбор —
    нет. Проверять баланс автоматически.

## Персональные данные

Собираем о клиенте: Telegram ID, имя, телефон, дата события, гости, бюджет,
комментарий. Только по раздельному согласию, **с журналом**: что, когда,
версия текста, возможность отзыва.

О вендоре: название, категория, район, фото без лиц, телефон, ФИО контактного
лица, СТИР, адрес, отметку о проверке.

**Не собираем:** паспорт и сканы, ПИНФЛ, дату рождения, фото лица, точную
геолокацию.

СТИР сверяется с открытым реестром, **скан не храним** — храним отметку о
проверке.

Вендор видит о клиенте ровно то, на что тот дал согласие. Выгрузка базы
клиентов недоступна ни в каком виде.

В коде API схема `pii` (таблицы и функции `read_*`) упоминается только в
`apps/api/src/db/pii.ts`: новое чтение или запись ПДн — правка этого модуля.
Упоминание в любом другом файле `src` роняет тест `db/pii.test.ts`.
